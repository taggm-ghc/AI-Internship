## Why this process exists, not just what it is

Two hubris-shaped failure modes this process exists to guard against, named explicitly because the steps below are pointless if the reasoning behind them stops being visible:

1. **Uninformed knowledge is assumed outdated or wrong, not merely incomplete.** Whatever this session already believes about a domain -- from training, from memory, from an earlier pass over this codebase -- is a hypothesis until checked against something current and external. Step 5 is not a formality that follows a plan already believed correct; it is the check that the plan might not be.
2. **Focused attention is myopic by construction.** Solving the narrowly-scoped problem well is not the same as having scoped it correctly -- a plan can be internally consistent and still miss a frame a domain expert or a published lessons-learned writeup would have caught immediately. Step 5's searches should include at least one aimed at the domain broadly (what do practitioners get wrong here, what's the known failure mode) -- not only searches that confirm or fill in the plan steps 2-4 already drafted.

Every other step here is mechanical; these two are why skipping or rubber-stamping steps 5-6 defeats the point of the Skill.

**Task drift (added 2026-09-23, same-session finding):** a long session nests work -- a job contains tasks, a task contains activities, an activity reaches milestones -- and drift at any level is invisible to a check that only compares against the top-level goal. A tangent can stay perfectly consistent with its own immediate parent while that parent has already drifted from *its* parent one level up; checking only against the session's original ask misses that, because each local step still looks justified. **The check is against the immediate predecessor, one level up, not a re-derivation from the top every time** -- when resuming or continuing nested work, state explicitly what the current unit is in service of at the next level up (this activity serves this task; this task serves this job), not just "does this still matter" in the abstract. Cheap to do, and it's what catches a chain of individually-reasonable steps that has collectively wandered.

## The process

1. **Strategize.** Work out the actual approach before writing anything formal down -- what's being built or changed, why, and the main design choices and their tradeoffs. This can start as loose reasoning, but nothing here is the durable record yet.

   **1a. Goal alignment.** Name what the initiative serves, specifically: a curriculum deliverable (week/session/module #.#), a graded assignment requirement, a p3m3 digest item, or an explicit user goal. State its **success determinants** (what observable result means it worked; measurable where possible, e.g. "doc_hit@5 rises on the 200-question eval") and its **milestones**. Check it against the programme end date (2026-10-12) and anything already paused or deferred. If it aligns with nothing, say so and ask; don't build it on momentum. Label its origin honestly: required, a user decision, or an optional extra (and from where).

   **1b. Gap analysis.** **Baseline**: what already exists that bears on this, verified by reading or running it, not assumed. **Target**: what the success determinants require. **Gaps**: the difference. For each gap, name the **bridge** (the real fix) and, if the bridge is slow, a **workaround** (a temporary measure, labelled temporary). List dependencies and the resources each bridge consumes (step 3's categories). Existing assets that close a gap outright are the cheapest bridge; name them.

   **1c. Alternatives.** Before committing to one design, write down **at least three**: (i) **defer / do nothing**, with its real cost; (ii) the **simplest workable shape**, which per module 3.12 is often a deterministic workflow or one model call rather than an agent, and per module 3.4 a single agent rather than several, **unless** a phase needs isolation (a quarantined, tool-less reader for untrusted content; an evaluator independent of the generator) or genuinely parallel work; (iii) the proposal itself. Add others where they're genuinely different, e.g. a hosted service vs. a local library. Steps 3–4 then flow and pseudocode the leading candidate(s), not just the first idea.

2. **Propose the plan, recorded in p3m3 immediately.** A new permanent ID (or an extension of an existing item) in `p3m3/todo-digest.md`, with deliverables/dependencies/requisites in the format already established there -- before any code exists, not documented after the fact.

3. **Logically flow it, including resource requirements.** A step-by-step flow (what calls what, data/control flow through the system, request/response shapes) plus what it actually costs to run: external API calls and roughly how many, new dependencies introduced, DB reads/writes added, and any other consumed resource -- qualitative and directional, not a fabricated number. Mandatory for any multi-step build, not optional.
   
   **Flow as a checkable graph.** Flows are recorded as Mermaid flowcharts using 7PMG conventions (one start and end, verb-object labels, ≤50 nodes before decomposition, structured joins/splits). Verify soundness: every node reachable from start (no dead activities), every node can reach end (no deadlock), every decision node has ≥2 labelled exits. At build time, compare the designed flow with the compiled agent's `get_graph().draw_mermaid()` to catch drift.

4. **Generate pseudocode for the implementation**, in the same subsection, so the shape of the real code is settled on paper before it's settled in a file.

5. **Search the web for literature, production lessons-learned, and de-facto standards** relevant to the domain -- not just local codebase patterns. This runs against the step 3-4 draft, deliberately after it exists: research stress-tests a concrete proposal instead of the plan being assembled purely from search results. At least one search must target the domain broadly -- known failure modes, what practitioners get wrong, the de-facto standard -- not only queries phrased to confirm or fill in what steps 2-4 already assumed; a search that can only agree with the plan can't catch a wrong frame.

   **Entry (added 2026-10-02).** Before any search: (1) Read `research_config.json` and record its `config_version` and `config_sha256` (SHA-256 of the canonical JSON); every findings file carries both. (2) Choose a profile from `profiles` and state in the plan which one and why. (3) Write the testable sub-claims (5a(i), now an entry criterion). (4) Split the budget across roles from the profile's `max_calls_per_plan` and the `budgets.*` keys; no budget is invented in a prompt. (5) Before every spawn, check `recursion.max_depth`, `recursion.max_children_per_agent` and `recursion.max_agents_per_tree`. Researchers run as the `researcher` agent; the antagonistic angle runs as `adversarial-researcher`.

   **Proportionality.** Two profiles, both defined in config: **rapid** (a small budget; the antagonistic search stays mandatory; the verifier checks load-bearing sources only; the red-team is optional, and its absence is recorded in the plan) and **standard** (every step below). Rapid reviews are an accepted practice in software engineering (plan section 7, F5, F6); a small question does not need a full review, but it never skips the contrary search.

   **Submission path (Job 16, 2026-10-03):** agents submit through the recorder server under a binding the orchestrator issues first (5b), and 5d's lint is both the server's check and the orchestrator's independent one.

   **Order of the research stage:** entry → confirming, domain-broad and antagonistic searches (5, 5a(ii)–(iv)) → findings files (5b) → lint on the findings (5d) → red-team (5a(v)) → citation verification (5c) → `synthesizer` verdict table → step 6 → lint with `--plan` (5d) → 6a.

   **5a. Adversarial search (added 2026-10-02, user direction; (i), (iii), (iv) and (v) tightened the same day).** Step 5 must also look for **competing, contradictory, disproving and otherwise antagonistic epistemic sources**, from **reliable portals**, not only sources that agree. (i) State the claim or plan as testable sub-claims (done at entry, before any search); (ii) for each, search for the strongest source *against* it and for a competing alternative, using different vocabulary from the confirming queries (the opposite term, the known failure mode, the critique, the retraction/replication); at least `min_antagonistic_per_subclaim` antagonistic rows per sub-claim, or a Gaps line saying none was found within budget; (iii) prefer reliable portals and rate each source: **high** = peer-reviewed or preprint indexes and standards/government bodies; **medium** = official vendor or engineering documentation and postmortems; **low** = blogs, forums, listicles (use only as leads; exclude SEO content farms). The domain patterns for each tier live in config `reliability_tiers`. The portal tier is the **default prior, not the verdict**: a rating may move one level with a stated reason (`medium (override: <reason>)`, required by `reliability_override_requires_reason`), judged on authority, method, date and objectivity (Garousi et al.'s multivocal-review approach, plan F7). Grey literature is admissible as evidence of practice, not of effect; (iv) record for every source its **read state**, one of `read_status_values`: `READ-VERBATIM` (the raw page text was seen), `READ-SUMMARIZER` (fetched through a tool that summarises the page; WebFetch does, so a fetched page is this state unless the raw text was seen), `SUMMARY` (search-result summary only), `TITLE-ONLY`, `FETCH-FAILED`. A quote from anything other than `READ-VERBATIM` is a paraphrase and is prefixed `~`. Never present a summary-only source as verified; (v) **red-team the findings too**: after the first pass, run a second pass whose only job is to undermine the first pass's conclusions. The red-team is a **separately spawned `adversarial-researcher` in `red_team` mode, by definition name, never a fork** (a fork inherits the researcher's context, so it is not independent). Its inputs are the findings files and the sub-claims only: not the plan's rationale, the researchers' transcripts or the preferred alternative. It must ground its critique in fetched external evidence, not reasoning alone (LLMs do not self-correct reliably without external feedback, plan F2; LLM evaluators favour their own output, plan F3; both limits apply within one model family, which is why D3 is a recorded divergence). Under the rapid profile the red-team may be skipped, and the skip is recorded; (vi) report honestly which sub-claims **survived**, which were **overturned or qualified**, and where **no evidence exists** (say so rather than filling the gap). Step 6 then records each antagonistic finding, and what it changed or why it did not.

   **5b. Findings file and evidence chain (added 2026-10-02).** Every research agent returns one findings block in the schema of the plan's section 5.3; before spawning agents the orchestrator issues each a binding with `p3m3/issue_research_binding.py`, and agents submit their findings block through the recorder server's `submit_findings` tool, which writes it to `<findings_dir>/<research_id>-<role>-<n>.md` (the orchestrator no longer re-types agent output; any orchestrator edit to a findings file is logged in an edit log) (`findings_dir` from config; a copy is promoted to `p3m3/research-logs/` only when a plan cites it). The first line is a `research-header` JSON comment (research id, plan, role, angle, model, parent, depth, `config_version`, `config_sha256`, budget limit and used, date, sub-claims). The source table has **one URL per row** and a stable source id per row, with read state, reliability, a quote of at most `quote_max_words` words, sub-claim, stance, strength and `verifier_status`; then a `## Gaps` section and a `## Verdicts` table (`survived`, `qualified`, `overturned`, `no-evidence`). **Evidence chain, in the plan:** (1) every factual claim cites `[src:ID]`, or `[measured:<file or run id>]` for our own measurement; (2) a claim labelled verified or validated, a decision, or a 6a score may not rest **only** on sources whose read state is in `evidence_chain.blocking_read_states` or whose `verifier_status` is `MISMATCH` or `UNVERIFIED`; (3) a number in a claim must appear in a cited row's quote, or be cited as our own measurement; (4) every cited id must exist in a findings file given to the lint.

   **5c. Independent citation verification (added 2026-10-02).** A fresh `citation-verifier` agent (never a fork) re-fetches every **load-bearing** source: one cited by a decision, a 6a score or a "verified" label (the profile's `verifier_scope`; budget `budgets.verifier_calls` plus `budgets.verifier_slack`). It receives those rows **with the quote column removed** and the sub-claims, extracts the supporting passage blind, and only then compares it with the researcher's quote. It checks id → title → author → date, and that the quote and any number are present. Its status (`VERIFIED`, `MISMATCH` or `UNVERIFIED`) goes into the row's `verifier_status`. A non-`VERIFIED` status downgrades the claim's wording (to unverified, or qualified); it never hides the claim. Under the standard profile, R1 then spot-checks `verification.human_spot_check_count` randomly chosen load-bearing citations: the only check outside the model family.

   **5d. Lint gate (added 2026-10-02).** Run `check_research_log.py` (this Skill's directory) on the findings files with `--config research_config.json`, and again with `--plan <plan file>` once the step 6 revisions are drafted. A non-zero exit blocks step 6 (findings) or the 6a ranking and step 8 (plan). The recorder server lints on submission and returns errors to the author agent in the same exchange, so the author fixes and resubmits in the same turn; the orchestrator's own `check_research_log.py` run is the independent check. The number of fix attempts is `lint.max_fix_attempts`. When attempts run out, fail verbosely: record the evidence gap in the plan, drop or downgrade the claim, and report the blocker to R1 with saved state. A fingerprint mismatch means the findings ran under another config version: re-run, or lint with that version's config. Pre-schema findings files are reported with `--legacy` (counts only; not graded). The lint checks form, not truth: a clean run is not a verification, which is why 5c exists.

6. **Review and revise the p3m3 entry against what step 5 found.** For each finding that changes the flow or pseudocode, edit the p3m3 entry itself and say explicitly what changed and why, citing the source -- not a separate note that never makes it back into the durable record. A finding that doesn't change anything is still worth a brief mention, so it's clear research happened rather than assumed. This is what makes the plan research-*informed*: the p3m3 record has to actually reflect the research, not just this session's memory of having done it. **(2026-10-02)** Each revision note cites the source ids it rests on (`[src:ID]`, 5b). The `synthesizer` agent's verdict table (sub-claim, verdict, supporting ids, antagonistic ids, weakest link) is copied into the p3m3 entry as-is, not reworded.

   **6a. Rank the alternatives, on evidence.** Score each alternative from 1c on **feasibility** (can it be built and verified in the time available?), **effectiveness** (does evidence say it meets the success determinants?), **cost/risk** (latency, spend, memory, new dependencies or credentials, blast radius on production) and **strategic fit** (1a). Use qualitative levels (item #28: no false precision), each backed by a cited source or a measured result, not by how the proposal reads. **Guard against self-grading:** the one ranking the options usually also wrote the proposal, which is the self-evaluation bias this project has measured literature on (LLM judges favour their own output). So ground every score in external evidence or data, prefer a measured comparison (an eval run) whenever one is cheap, and when two options are close or the trade-off is a value judgment, present the ranking to the user as a decision rather than picking silently. Record the ranking and the reason the winner won in the p3m3 entry; losing alternatives stay recorded, since they're the fallback if the winner fails verification. **(2026-10-02)** Every score cites source ids or a measured result; a score resting only on summary-level sources (read states in `evidence_chain.blocking_read_states`) is labelled **weak**. The per-criterion evidence summary is drafted by the `synthesizer` agent, which did not write the proposal and adds no sources; the author presents it and does not re-score it.

7. **Where research surfaces authoritative source material, ingest it.** `POST /ingest` the real source (full text via `WebFetch`, verified author/date -- don't trust search-result summaries alone) with a real `provenance` payload (source, source_url, author, published_at, fetched_at, `provenance_type`). This makes the design decision citable from inside the running app's own RAG corpus, not only from a planning document that lives outside it. **(2026-10-02)** Ingest only sources whose `verifier_status` is `VERIFIED` **and** that pass the licence gate (#63: the original source's licence prevails; NC/ND declared is rejected; no declared licence is held for human review). Never ingest a row whose read state is `SUMMARY`. Findings files themselves are planning records and are never ingested. **(2026-10-02, R1 direction)** Research agents delegate ingest to the `ingester` agent (repository root `.claude/agents/ingester.md`, a leaf) instead of calling the API themselves: the orchestrator writes a manifest plus the verbatim text files (research agents stay read-only), the ingester dry-runs `scripts/ingest_manifest.py`, and runs `--write` only when the user has approved that specific ingest. This path never uses `POST /ingest/versions/accept`, which stays `INGEST_API_KEY`-gated for humans and external actors.

8. **Then implement**, against the reviewed p3m3 entry -- not against the plan-mode scratch file or step 1's loose reasoning, both disposable.

9. **Verify end-to-end, by actually running the code**, not by reading it. This project has been burned by exactly this gap more than once: a syntax check (`ast.parse`, `python -c "import ..."`) catches typos, not runtime bugs -- e.g. a Streamlit `st.page_link()` call to the entrypoint script that only failed with `StreamlitPageNotFoundError` when actually executed via `streamlit.testing.v1.AppTest`, or a DataFrame column with dict values that only broke PyArrow serialization when a chart actually rendered. Prefer the tool that runs the real code path (`AppTest` for Streamlit pages, a live local server + real HTTP calls for API endpoints) over one that only parses it.

10. **Maximize component reuse deliberately, not as an afterthought.** When a second file needs logic a first file already has, extract the shared logic into its own importable module rather than duplicating it -- duplication is a standing source of drift and bugs (two copies of a cold-start-retry helper silently diverging is a real failure mode this project hit). State it in the plan when a new piece of work will share logic with existing code, and name what's being reused and what's new.

11. **Define or refine deterministic tools and agentic Skills, not just narrate the process by hand.** Step 10 is reuse *within* an effort; this is reuse *across* efforts. Where step 9's verification, a repeatable check, or the research-to-corpus pipeline (steps 5-7) will recur on future work, capture it as a script (matching `verify_operational_store.py`/`golden_eval.py`'s existing pattern -- runnable, not just described in prose) or as its own Claude Code Skill (matching this Skill itself and `rag-scaffold`), rather than re-deriving or re-narrating it from scratch next time. Decide explicitly, per effort: does this introduce a deterministic check worth scripting, or a repeatable planning/execution pattern worth its own Skill -- and if so, build or refine it as part of this effort, not as a someday follow-on. **(2026-10-02)** The research stage already has its reusable artifacts: the four agents (`researcher`, `adversarial-researcher`, `citation-verifier`, `synthesizer`, in the repository root's `.claude/agents/`), the lint `check_research_log.py` and the config `research_config.json` (both in this Skill's directory). Run them; do not re-derive their prompts or checks. A change to any config value is a new `config_version` (which changes the fingerprint), never an edit in place.

## Why the main session delegates the research stage (2026-10-02)

The session running this Skill is an orchestrator. Searching, fetching, reading sources and verifying citations are bulk work whose raw material would otherwise sit in the main context for the rest of the session; the agents below read it in their own context and return only a findings block, a verdict or a table. Keep the main session for the plan, the decisions and the user. Check what comes back (the lint and the verifier exist for this). See the repository's `AGENTS.md`.

## What this replaces

Claude Code's `EnterPlanMode` still applies for the actual step-by-step design/pseudocode work, but its output (a file under `~/.claude/plans/`) is a scratch draft, not the deliverable. The p3m3 entry from step 2, kept current through step 6, is what persists and what future sessions read -- write the plan there, not only in the ephemeral plan file, before treating planning as done.
